1. 한 줄 정의

터미널에서 실행하는 AI 개발 클라이언트다. CLI를 겉에서 감싸는 방식이 아니라 각 제공자의 공식 백엔드에 직접 붙고, 화면과 입력 계층만 직접 소유한다. 그래서 어떤 모델을 쓰든 같은 규칙·같은 역할 체계·같은 화면으로 작업할 수 있다.

핵심 가치는 모델을 바꾸는 데 있지 않고, 모델에 들어가는 지침을 제품이 소유하는 데 있다. 사용자가 각자 설정 파일을 만들어 두지 않아도 팀 전체가 같은 동작을 얻는다.

2. 프롬프트 제어로 만드는 정형 동작

2-1. 무엇을, 언제 주입하는가

지침역할주입 시점
전체 규칙 (제공자별 2벌)한국어 출력, 응답 형식, 작업 목록, 근거 제시 등 기본 규칙 전체새 대화 시작 시 + 세션 재개 시 재전송
턴 리마인더규칙 요약 한 줄로 매 턴 상기매 턴
역할 블록현재 에이전트 역할의 지침과 분량 규칙매 턴
지식 기록 블록auto-knowledge On/Off에 맞는 기록 지시매 턴 (실행 중 추가 입력 때도 이것만 갱신)
질문 처리 지침선택지·승인 요청 방식 고정대화 설정으로 전달
  • 재개 시 재전송이 핵심이다. 이전 세션은 당시 문구가 기록된 채 재생되므로, 다시 보내지 않으면 오래된 세션이 옛 규칙으로 계속 돈다.
  • 브리지가 재기동될 때도 다시 채운다. 세션을 되살리는 것은 새로 여는 것과 같아, 여기서 빠뜨리면 규칙 없는 세션이 열린다.
  • 임시 곁가지 대화에도 같은 지침이 실린다.

2-2. 제공자마다 넣는 자리가 다르다

제공자전체 규칙이 들어가는 곳매 턴 추가분
Claude세션의 시스템 프롬프트. 기본 프리셋을 대체하지 않고 덧붙인다역할·지식·리마인더를 사용자 턴 앞에 붙였다가 화면 표시 때 제거
Codex대화의 developer instructions추가 컨텍스트로 전달하되 이미 상시 들어간 항목은 중복 제거

제공자를 바꾸면 대화 인계 블록이 만들어진다. 아직 전달되지 않은 기록만 골라 요약해 넘기고, 분량이 넘치면 오래된 것부터 생략했다고 표시한다. 새 모델에게는 "이미 끝난 작업을 반복하지 말고, 인계 사실 자체를 사용자에게 언급하지 말라"고 지시한다.

2-3. 무엇이 정형화되는가

  • 한국어 출력 강제 — 최우선 규칙으로 격상되어 있다. "사용자에게 보이는 문장의 첫 글자는 마크다운 기호를 빼면 한글 음절이어야 한다"까지 지정하고, 영어 판정 코드도 괄호 안을 포함해 한국어로 바꾸게 한다. 이 문구가 사라지지 않도록 자동 테스트가 상시 검사한다.
  • 작업 목록 강제 — 여러 단계·두 번 이상의 도구 호출·설계 판단이 필요하면 첫 작업 전에 반드시 목록을 만들게 한다. 번호를 직접 붙이고, 시작 직전 진행 중으로, 끝난 직후 완료로 바꾸며, 동시에 진행 중인 항목은 하나로 제한한다. 도구 이름은 제공자에 맞춰 갈린다.
  • 응답 형식 — 결론부터 불릿으로, 서론·인사·맺음말·이모지 금지, 한 불릿에 한 쟁점, 사용자 영향과 필요한 조치를 먼저. 문단 사이 빈 줄까지 지정한다.
  • 완료 표현 통제 — 실제로 변경을 마쳤을 때만 완료형으로 끝내게 한다. 조사·질문·설명에는 완료 표현을 쓰지 못한다. 보고가 실제 수행보다 앞서 나가는 것을 막는 장치다.
  • 근거 제시 규칙 — 현재 구현·과거 원인·추정을 구분하고 근거가 없으면 "미확인"으로 쓰게 한다. 검색 한 번 실패로 기능이 없다고 단정하지 못하게 하고, 외부 상태는 실제 응답 전까지 완료·거절을 단정하지 못하게 한다. 무응답을 승인으로 해석하는 것도 금지한다.
  • 질문·승인 방식 고정 — 선택지는 전용 도구로 묻고, 도구가 실패하면 일반 문장으로 번호를 붙여 다시 묻게 한다. 취소·빈 답변·시간 경과는 승인이 아니다.
  • 지식 기록(auto-knowledge) — 읽기는 설정과 무관하게 항상 강제한다. 프로젝트에 지식 폴더가 있으면 인덱스부터 읽는다. 쓰기만 On/Off로 갈리며, 설정은 작업 폴더별로 저장되고 기본은 꺼짐이다. 두 문구 모두 "이전 상태 지침을 대체한다"를 포함해 규칙이 누적 충돌하지 않게 한다.

2-4. 지침이 흔들리지 않게 하는 장치

  • 출력 스타일을 기본값으로 고정한다. 사용자 환경의 출력 스타일이 제품 지침 위에 얹히지 않게 하기 위해서다.
  • 지침 문구의 존재·부재를 자동 테스트가 검사한다. 예를 들어 공통 지침에 분량 상한 숫자가 다시 들어오지 못하게 막는다. 분량은 역할이 정하기 때문이다.
  • 역할 프롬프트가 특정 외부 도구 어휘를 흘리지 않는지도 테스트한다.

3. 에이전트 역할

Tab 한 번으로 역할이 바뀌고, 역할은 다음 턴의 지침과 쓰기 권한을 함께 바꾼다. 내장 역할은 5개다.

역할책임쓰기 권한분량
Builder (기본)일상 개발. 필요한 코드만 쓴다는 규칙 아래 구현한다제한 없음공백 제외 200자
Planner저장소 사정을 모르는 사람도 추측 없이 실행할 수 있는 계획을 쓴다. 구현은 하지 않는다계획 폴더만상한 없음
Researcher출처 있는 조사 결과를 내고 확인된 사실·추론·공백을 구분한다없음(읽기 전용)상한 없음
Reviewer변경이나 계획을 의도와 대조해 근거·심각도·판정을 낸다. 수정은 하지 않는다없음(읽기 전용)상한 없음
Goal Runner구현·검증·검토·증거까지 끝내 완수한다. 부분 완료나 미검증을 완료로 보고하지 않는다제한 없음상한 없음

3-1. 역할별 세부 규칙

  • Builder — 구현 선택 사다리가 정해져 있다. 추측성 요구사항 생략 → 기존 코드·패턴 재사용 → 표준 라이브러리 → 플랫폼 기본 기능 → 이미 설치된 의존성(새로 추가 금지) → 한 줄 → 그래도 안 되면 최소 동작 코드. 구현이 하나뿐인 인터페이스, 상수용 설정, 미래 확장 지점 같은 불필요한 추상화를 금지한다. 200자 제한은 선택·승인 설명과 코드 블록에는 적용되지 않는다.
  • Planner — 작업을 소규모 조사·한정 범위·구조 변경으로 분류하는 게이트를 먼저 통과한다. 최종 보고는 목표·주요 작업·검토 결과·미확정 사항·계획 경로의 고정 불릿으로 낸다.
  • Reviewer — 사양 → 동작 → 근본 원인 → 구조 → 코드·테스트 → 준비도의 6단계 순서를 따르고, 심각·보통·경미 3단계와 고정 출력 형식(판정·문제·재검토·미확인)을 쓴다. 서브에이전트를 만들지 않는다.
  • Goal Runner — 검증 강도를 세 단계 중에서 스스로 골라 선언하고, 실행 산출물을 별도 폴더에 남기며, 검토 대상을 해시로 고정한다. 수정 회차 상한은 5회이며 4회차부터는 새 최상위 모델 에이전트가 맡는다.

3-2. 역할 지침 전달과 절차 가이드

  • 역할 블록은 매 턴 전달되며 "이전 역할 블록을 모두 대체한다"고 명시한다. Builder도 예외가 아니어서 역할을 되돌리기 위한 별도 턴이 필요 없다.
  • Builder 외 모든 역할에는 "분량 상한이 해제된다"는 문장이 함께 들어간다. 분량 규칙은 역할이 소유한다.
  • Planner만 절차 문서를 분리해 로컬 캐시에 풀어 두고 경로만 넘긴다. 그리고 "각 단계의 첫 읽기·명령·수정 전에 해당 가이드를 전부 읽어라, 읽기에 실패하면 그 단계를 미완으로 두고 추측하지 말라"는 게이트를 건다. 매 턴 본문에 통째로 싣지 않아 토큰이 절약된다. 캐시 준비에 실패하면 전문을 본문으로 대체한다.
  • 사용자 정의 역할 — 지정 폴더에 파일 하나가 역할 하나다. 머리말에 표시명과 한 줄 설명을 적고 본문이 그 역할의 지침이 된다. 내장 역할 이름은 빼앗을 수 없고, 변경 반영에는 앱 재시작이 필요하다. 도구 권한이나 모델 지정은 역할의 개념에 없어 옮겨지지 않는다.

3-3. 쓰기 권한은 프롬프트로만 막지 않는다

  • Claude — 역할의 도구 정책을 턴마다 함께 보내고, 사전 훅이 도구 호출 자체를 차단한다. 훅은 권한 모드와 무관하게 동작하므로 읽기 전용 역할은 우회 모드에서도 유지된다.
  • Codex — 쓰기 가능 경로가 아예 없을 때만 읽기 전용 샌드박스로 턴을 돌린다. 경로 범위 지정이 없어 Planner의 계획 폴더만 쓰기는 여기서는 프롬프트 수준 약속으로만 유지된다.

3-4. 서브에이전트 레인 4종

Planner와 Goal Runner가 이름만 지정하면 모델과 도구 범위가 고정된다. 모델을 고르지 않은 호출이 세션에서 가장 비싼 모델을 물려받는 일을 막기 위한 설계다.

레인용도도구 범위
implementer계획의 한 작업을 그대로 구현읽기·수정·쓰기·셸
reviewer작업 단위 검토읽기 전용
senior reviewer전체 변경·엄격 검토·구조 검토 (최상위 모델)읽기 전용
qa실제 화면을 두드려 깨뜨리는 적대적 테스트읽기 전용

기존 정의 파일을 갱신할 때 사용자가 손댄 프롬프트는 건드리지 않는다.

4. provider 인증 활용과 사용자 편의

4-1. 무엇을 쓰고 무엇을 쓰지 않는가

  • 별도 API 키를 쓰지 않는다. Claude 경로는 이미 설치·로그인된 Claude Code의 구독 로그인 저장소만 사용하며, 자식 프로세스 환경에서 API 키 환경 변수를 코드로 제거한다. 선언만이 아니라 구현으로 확인된다.
  • 공식 경로만 쓴다. Claude는 공식 Agent SDK, Codex는 공식 app-server에 붙는다. 자체 토큰 저장소, 프록시, 비공개 엔드포인트 호출 코드는 조사 범위에서 발견되지 않았다.
  • 자신을 숨기지 않는다. 각 백엔드에 클라이언트 이름을 그대로 전달해 서드파티 클라이언트로 식별된다.
  • 사용 범위를 스스로 제한한다. 이 경로는 본인 계정의 로컬 개인 사용용이며, 로그인 공유나 제3자 인증 화면으로 제공하지 않는다고 문서에 못 박고 있다. 실행 파일에는 공개 식별자만 포함되고 토큰이나 비밀키는 들어가지 않는다.
  • 기본 동작을 대체하지 않고 덧붙인다. 시스템 프롬프트는 기본 프리셋에 덧붙이기만 하고, 도구도 기본 구성을 그대로 쓴다. 원래 CLI가 하던 일을 빼앗지 않는다.
  • 설치된 CLI가 내장 번들보다 최신이면 설치본을 우선 실행한다. CLI만 업데이트해도 새 모델을 쓸 수 있고 제품의 새 배포를 기다리지 않아도 된다.

4-2. 그래서 사용자가 얻는 편의

  • 설정이 없다. 키 발급이나 환경 변수 설정 없이, 이미 쓰던 구독 로그인 그대로 터미널에서 바로 시작한다.
  • 종량 과금 걱정이 없다. API 키 경로를 쓰지 않으므로 구독 한도 안에서 동작한다.
  • 사용 한도가 항상 보인다. 하단 상태줄에 5시간 창 사용률과 남은 시간 카운트다운, 주간 사용률이 상시 표시되고 플랜 등급도 라벨로 나온다. 컨텍스트 잔량도 함께 보인다.
  • 한도에 걸려도 방치되지 않는다. 한도에 도달하면 초기화 시각을 받아 대기 상태로 들어가고, 시각이 되면 자동으로 이어서 진행한다. 대기는 언제든 취소할 수 있다.
  • 제공자를 갈아탈 수 있다. 명령 한 번으로 전환하고, 이전 대화 요약이 자동으로 인계된다.
자동 재개는 조건이 좁게 잠겨 있다. 오류가 한도 거절이고, 구독 한도 유형이며, 추가 과금을 쓰고 있지 않고, 초기화 시각이 24시간 이내이며, 재시도 3회 미만일 때만 예약한다. 일반 오류나 추가 과금 사용 중에는 예약하지 않는다. 또한 재개할 때 원래 프롬프트를 다시 보내지 않는다. 부작용이 있는 명령이 두 번 실행되는 것을 막기 위해 "중단된 작업을 이어가라"는 고정 문구 하나만 넣는다. 절전 등으로 30분 이상 지났으면 자동 실행하지 않고 사용자를 기다린다.

5. 그 밖의 사용 편의

  • 사이드 패널 — 아직 커밋하지 않은 변경을 파일별로 펼쳐 보고, diff에서 드래그로 고른 줄을 다음 프롬프트에 바로 첨부할 수 있다.
  • 컴포저 자동완성 — 슬래시 명령, 플러그인·스킬·앱, 파일·폴더 검색(무시 규칙 존중).
  • 클립보드 이미지 붙여넣기가 첨부 덩어리로 삽입되어 커서 이동·삭제가 블록 단위로 동작한다.
  • 한글 입력 — 조합 중 글자를 컴포저가 제자리에 직접 그리고, 한글 붙여넣기 오작동도 타이밍 분류기로 처리한다.
  • 응답 중 프롬프트 대기열 추가, 실행 중 끼워넣기, 임시 곁가지 대화, 대화를 유지한 채 Git 작업 트리로 진입.
  • 표시 밀도 조절 — 응답·셸 출력·diff 표시량을 프리셋으로 한 번에 바꾼다.
  • 업데이트는 새 버전을 검증 후 다음 실행부터 전환하므로 실행 중인 세션이 끊기지 않는다. 점검 명령으로 제공자별 준비 상태를 확인한다.
  • 제공자가 지원하지 않는 명령은 목록과 도움말에서 함께 숨겨져, 쓸 수 없는 기능이 애초에 보이지 않는다.

6. 미확인 · 주의 사항

  • QA는 내장 역할이 아니다. 사용자가 고르는 내장 역할은 5개이며, QA는 Goal Runner가 호출하는 서브에이전트 레인이다.
  • 200자 제한은 Builder 전용이다. 공통 지침에는 분량 상한이 없다.
  • Planner의 쓰기 경로 제한은 Claude에서만 기계적으로 강제된다. Codex에서는 프롬프트 수준 약속으로만 유지된다.
  • 지침 준수는 강제가 아니라 유도인 항목이 많다. 지식 기록이나 사용자 정의 역할 준수는 모델의 이행에 달려 있고 코드로 검증되지 않는다고 내부 문서가 밝히고 있다.
  • 비용 표시 — 비용 계산 로직은 있으나 내부 문서에 "현재 비용 배지 미표시"로 적혀 있어 화면 노출 여부는 확인이 필요하다.
  • 자동 재개 실검증 없음 — 실제 계정 한도 소진·초기화 상황에서의 동작은 내부 문서 기준 미검증으로 기록되어 있다.
  • 제공자 이용약관 적합성은 저장소 문서만으로 판단할 수 없다. 이번에 확인한 것은 구현이 공식 SDK·공식 서버 경로만 쓴다는 사실까지다.
근거는 저장소 소스 코드와 내부 지식 문서다. 날짜가 붙은 검증 기록은 당시 결과이므로 현재 구현과 다시 대조해야 한다.
