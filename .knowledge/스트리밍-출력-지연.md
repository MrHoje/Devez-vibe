# 스트리밍 출력 지연과 일괄 표시

적용 범위는 이미 받은 응답을 화면에 흘려 보이는 속도다. 확인 위치는 [src/state.rs](../src/state.rs)의 `TextPace`·`drain_stream_text`·`release_held_notifications`, [src/renderer.rs](../src/renderer.rs)의 `hidden_streaming_link_range`다. 모델·네트워크의 수신 대기는 별개이며, SDK 구독 한도 대기는 [Claude SDK 문서](Claude-Agent-SDK-호환성-업데이트.md)를 본다.

## 증상별 원인과 해결

| 증상 | 원인 | 해결(버전) |
| --- | --- | --- |
| 긴 답변이 점점 뒤처지다가 완료 순간 한꺼번에 표시 | 속도 수요를 대기 전체가 아니라 현재 줄 길이로 계산해 짧은 줄이 많은 답변이 초당 약 80자에 묶였다(1.8.16~1.9.25). 뒤처진 양은 완료 뒤 따라잡기나 과거의 1.5초 전량 출력으로 한 번에 나왔다 | 수요는 대기 전체에서 숨긴 링크 주소만 빼서 계산하고, 한 번에 내보내는 범위만 현재 줄 끝으로 제한한다(1.9.26). 회귀 검사는 `many_short_lines_keep_pace_with_arrival` |
| 완료 뒤 1.5초가 지나면 남은 글자 전량 출력 | 완료 알림 보류에 1.5초 기한이 있었다 | 기한을 없애고, 남은 글자를 다 보일 때까지 완료 알림을 보류한다(1.9.22) |
| 짧은 답변이 몇 글자 뒤 통째로 표시 | 1.9.22 따라잡기가 경과 시간과 무관하게 한 번에 최대 512자를 꺼냈다 | 따라잡기 예산을 경과 시간에 비례시키고, 프레임당 줄 수도 제한한다(1.9.23) |
| 도구 실행 뒤 한참 멈췄다가 답변이 빠르게 쏟아짐 | 상류 몰림이다. Claude CLI 2.1.276 이후 도구 결과 다음 최종 답변의 약 절반에서 본문이 생성되는 동안 전달되지 않고 끝에 한꺼번에 도착한다. 같은 CLI의 Opus 4.8과 2.1.274 이전 Opus 5에서는 없었다. 호스트는 몰려 온 약 1,000자를 초당 약 1,200자로 풀어 1~2초에 보여 준다 | 호스트에서 멈춤은 줄일 수 없다. 표시 속도 상한을 초당 300자로 낮춰 몰려 온 1,193자를 약 5초에 걸쳐 풀어낸다. 대기가 4KiB를 넘을 때만 초당 1,600자로 따라잡는다(1.9.27) |
| 긴 링크 뒤 문장이 늦게 나옴 | 화면에서 숨긴 링크 주소까지 한 글자씩 처리했다 | 숨긴 주소는 즉시 넘기고 속도·밝기 계산에서 뺀다(1.8.16) |

## 유지할 설계 규칙

- 속도 수요는 대기 전체로 계산한다. 코드·표 문맥 재확인을 위해 줄 단위로 끊는 것은 내보내는 범위에만 적용한다. 두 가지를 같은 값으로 묶으면 긴 답변이 다시 뒤처진다.
- 완료 알림을 보류했다면, 뒤따라온 알림도 원래 순서와 스트리밍 보호를 거쳐 재생한다. 보류 배열을 `dispatch_notification`으로 바로 풀면 중간의 새 delta 뒤에 온 완료가 다시 전량 출력한다. 전환용 저장은 화면 완료 처리 뒤에 한다.
- 전량 출력 기한 없이 따라잡을 때는 프레임별 글자·줄 예산을 함께 둔다. 숨긴 링크 주소와 유니코드 결합 글자는 보존한다. 이 대기 중에는 백엔드 정체 감지가 별도 완료 알림을 만들지 않게 한다.
- 처리 틱은 터미널이 보여 주는 한 프레임과 같지 않다. 여러 틱의 출력이 한 화면에 합쳐질 수 있으므로 예산은 실제 경과 시간에 비례시킨다.
- 링크 주소만 갱신돼도 클릭 대상과 줄 번호는 다시 그려야 한다. `links_changed`로 다시 그리기를 요청한다. `stream_fade_tail`에 숨긴 주소 길이를 세면 이미 표시한 링크가 다시 흐려진다.

## 진단 순서

1. 짧은 세션에서도 재현되는지 먼저 확인한다. 2026-09-23 보고에서는 누적 사용량과 세션 길이를 원인으로 먼저 의심했다. 실제로는 짧은 세션에서도 긴 답변이면 재현되는 답변 길이 문제였다.
2. 실행 버전을 확인한다. 실행 중인 `dvz.exe`의 명령줄에 있는 `versions\X.Y.Z` 경로로 판단한다. 업데이트 전에 띄운 세션은 옛 코드로 돈다.
3. 증상이 답변 길이에 비례하면 모의 수신 검사를 먼저 한다. 일정 속도로 delta를 넣고 4ms마다 `drain_stream_text`를 호출해 대기량이 계속 커지는지 본다. 이미 완료된 원문을 재생하는 검사에는 수신 간격이 없어 이 결함이 드러나지 않는다.
4. 렌더러 비용을 확인한다. 2026-09-23 측정에서 화면 기록 2,686블록이어도 프레임당 약 1ms였고, 화면 높이를 넘긴 답변도 프레임당 출력은 1KB 안팎이었다. 기록 길이를 원인으로 보려면 이 수치를 다시 재서 반박해야 한다.
5. 실제 수신 간격은 브리지를 단독으로 띄워 잰다([브리지 단독 구동](Claude-Agent-SDK-호환성-업데이트.md)). 새 세션에 긴 답변을 요청하고 `item/agentMessage/delta`의 도착 시각과 길이를 기록한 뒤, 그 기록을 모의 수신 검사에 그대로 넣는다. 2026-09-23 Opus 5.5 측정에서는 평균 초당 약 100자, delta 중앙값 5자였고 0.7~1초 공백이 잦았다. 이 기록을 넣었을 때 1.9.25는 초당 약 80~100자에 묶여 끝까지 밀렸고, 1.9.26은 100ms당 최대 16자로 고르게 나왔다.
6. 과거 답변이 상류에서 몰렸는지는 Claude 세션 JSONL로 판정한다. CLI는 블록이 끝날 때 항목을 기록하므로(측정 세션으로 확인), 같은 메시지 id의 앞 블록 기록과 300자 이상 본문 기록 사이가 수 ms면 본문이 한 번에 도착한 것이다. 사용량의 `thinking_tokens`가 수십 개인데 도구 결과 뒤 기록까지 수 초가 걸렸다면 그동안 본문이 생성되고 있었다. 새 세션에서는 재현되지 않을 수 있어, 문제 세션을 브리지 `session/fork`로 복사해 재면 재현됐다. 측정 뒤 사본 JSONL은 지운다.
7. 실제 화면 정체와 상류의 몰아 보내기는 `DVZ_PERF=1` 로그로 가른다. `reveal_gap_max`·`render_max`가 크면 호스트 정체, 둘 다 작은데 `backlog_max`가 크면 수신 몰림이다.
8. 브리지 쪽에서 설계상 한 번에 넘기는 경우는 둘이다. Opus 5.5·Fable 5.1의 진행 알림 생각 블록은 블록이 끝날 때 한 번에 넘긴다. 한국어 요청의 영어 진행문은 한글·줄바꿈이 나오거나 160자를 넘을 때까지 보류한다. 이 둘은 결함으로 보지 않는다.

## 시험 기준

- 정지 화면 시험만으로는 출력 지연을 잡을 수 없다. 시간 순서를 흉내 내는 시험이 필요하다.
- 링크: 이미 도착한 입력을 40ms 단위로 처리하면서, 짧은 주소와 4,096자 주소 뒤 다음 단어가 나타나는 시간을 비교한다. 수정 전에는 각각 720ms·2,880ms였고, 수정 후에는 둘 다 160ms였다.
- 긴 답변: 초당 약 600자로 받은 2,640자를 표시하는 데 수정 전에는 마지막 수신 뒤 약 29초가 더 걸렸고, 수정 후에는 약 0.8초였다.
