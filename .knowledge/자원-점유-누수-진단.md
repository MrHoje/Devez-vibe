# 자원 점유·누수 진단 (2026-09-11)

DevezVibe(dvz)와 DevezCode를 며칠 연속 사용한 Windows 환경에서 CPU·RAM·디스크 잔여물을 실측하고 소스를 감사한 기록이다. 실측값은 당시 결과이며, 코드 근거는 아래 경로와 대조해 확인한다.

## 디스크 — 확인된 누적 지점

* 업데이트는 `%LOCALAPPDATA%\DevezVibe\versions\<버전>`에 버전별로 설치한다. 정리 로직이 없던 동안 배포마다 약 265MB가 쌓여 17개 버전 4.5GB가 관측됐다. 지금은 `src/update.rs`의 `prune_versions`가 버전 전환 직후 새 버전과 실행 중인 버전만 남기고 지운다. 실행 중이라 파일이 잠긴 폴더는 실패를 무시하고 다음 업데이트에서 다시 지운다. 활성 버전은 `%LOCALAPPDATA%\DevezVibe\current-executable.txt`가 가리킨다.
* 테스트가 `%TEMP%`에 `devez-agent-guides-test-<pid>`, `devez-role-guides-test-<pid>-N`, `devez-agent-guide-blocked-<pid>`, `devez-account-tests-<GUID>` 폴더를 남기고 지우지 않는다. 테스트를 돌릴 때마다 PID별로 새로 생긴다.
* `%TEMP%`에는 릴리스 검증·QA 산출물(`devezcode-release-*`, `devez-release-*`, `devez-mcp-qa-*` 등)도 남는다. 이쪽은 작업 부산물이라 자동 정리 대상이 아니다.
* 입력 로그(`src/input_log.rs`)와 화면 로그(`renderer.rs`의 `ScreenLog`)는 기본 꺼져 있지만 켜면 로테이션 없이 무한 append된다.

## 프로세스 — 고아가 남는 구조

* dvz는 백엔드를 `CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW`로 띄운다(`src/child_process.rs`). `child.kill()`은 직속 자식만 죽이므로, 손자 이하(백엔드 CLI가 띄운 MCP 서버, bash, python 등)를 정리하려면 별도 수단이 필요하다.
* 현재는 `adopt_backend`가 백엔드마다 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 작업 개체를 만들어 자식을 편입하고, 그 값을 백엔드 구조체가 들고 있다가 함께 버린다. 세션·제공자 전환으로 백엔드만 닫을 때도, dvz가 패닉이나 강제 종료로 끝날 때도 커널이 트리째 정리한다. 손자 상속과 트리 종료는 `child_process.rs`의 두 검사가 실제 프로세스로 확인한다.
* 진단 프로브(`src/doctor.rs`)와 `/shell`(`src/main.rs`)도 `output()` 대신 직접 spawn해 작업 개체에 넣는다. 프로브는 5초를 넘겨 결과를 버릴 때, `/shell`은 명령이 끝나거나 dvz가 먼저 끝날 때 개체가 함께 버려져 정리된다.
* `dvz update`가 실행하는 npm(`src/update.rs`)은 작업 개체에 넣지 않았다. 별도 프로세스 그룹으로 띄우지 않아 같은 콘솔에 붙어 있어 Ctrl+C와 창 닫기를 함께 받고, 완료까지 기다리는 동기 실행이라 남을 여지가 없다.
* 실제로 부모가 죽은 `postgres-mcp` 14세트(각 python 2개·conhost 1개 동반, 24~68시간 생존, 합계 약 520MB)가 관측됐다. 고아 conhost 개수·생성 시각이 고아 MCP와 일치한다.
* OpenCode는 `.cmd` 런처를 `cmd.exe /d /s /c`로 감싸 실행하므로(`src/open_code.rs`), kill이 래퍼만 죽이고 실제 `bun.exe`가 남았다. 작업 개체가 래퍼와 그 자식을 함께 잡으므로 지금은 정리된다.
* 패닉 훅과 콘솔 종료 핸들러는 여전히 없다. 프로세스가 사라지면 작업 개체 핸들도 닫히므로 백엔드 트리는 정리되지만, 종료 전에 해야 할 다른 마무리는 실행되지 않는다.
* DevezCode 쪽은 반대로 PTY 세션을 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` Job에 편입해 트리를 함께 정리한다. 다만 conhost는 Job 생성보다 먼저 만들어져 Job 밖에 있으므로 앱이 크래시하면 고아로 남을 수 있다.

## 유휴 CPU

* dvz의 유휴 소모는 계산량이 아니라 **깨어나는 횟수**가 지배한다. `src/main.rs`의 `STREAM_FRAME`이 4ms(250Hz)이고 해당 select 브랜치에 조건절이 없어 스트리밍 중이 아니어도 계속 돈다. 같은 파일의 `TimerResolution::raise()`가 `timeBeginPeriod(1)`을 앱 수명 내내 유지해 이 틱 레이트를 실제로 성립시킨다.
* 80ms 주기 `activity_tick`은 매 틱 콘솔 핸들을 3번 열고 닫는다(터미널 크기 조회 + 커서 위치 조회 내부에서 한 번 더).
* 더티 플래그는 정상 동작한다. 유휴 시 전체 재그리기는 일어나지 않으며, 스피너·shimmer 등 애니메이션도 조건부다.
* DevezCode는 종료 오버레이 스피너의 Storyboard가 `FrameworkElement.Loaded` + `RepeatBehavior="Forever"`로 걸려 있어, 오버레이가 `Collapsed`여도 앱 시작 직후부터 무한 애니메이션 클럭이 돈다(다른 스피너 15개는 `SpinnerSync`/`SpinnerActivator`로 게이팅됨). 유휴 CPU의 유력한 원인이나 프로파일러로 확정하지는 않았다.

## 메모리

* 화면 전사를 잘라낼 때는 제공자 전환·혼합 세션의 저장 원본을 따로 보존해야 한다. 화면용 `history`를 그대로 `provider_handoff_snapshot`에 넘기면 다음 저장에서 오래된 대화가 사라진다. 원문 블록 보관과 화면용 줄바꿈·선택 캐시는 별개이며, 화면 캐시 상한을 프로세스 전체 메모리 상한으로 설명하지 않는다.
* 재개를 최근 몇 턴으로 제한하려면 이전 기록을 다시 불러오는 경로와 전환용 원본 복원도 함께 필요하다. 단순히 페이지 순회를 중단하면 프롬프트 목록·이전 계획·혼합 세션 기록이 누락된다. 파일 크기에는 중복 이벤트·도구 데이터도 포함되므로 파일 바이트나 누적 입력 토큰을 화면 전사 크기로 취급하지 않는다.
* 과거 `render_fullscreen`은 매 프레임 `self.wrapped.clone()`으로 래핑된 전사 전체를 딥카피해 상주 2벌과 프레임별 전체 재할당을 만들었다.

* 전사 복제를 없애며 `render_fullscreen`이 `std::mem::take`로 `fullscreen_display_lines`를 꺼내 재사용하게 되자, 그 뒤에 도는 `reconcile_selection`이 비어 버린 필드와 새 전사를 비교해 전사 드래그 선택을 매 프레임 지웠다(1.8.27~1.8.33). 선택 구간의 지난 줄을 take 전에 복제해 인자로 넘겨 고쳤다. 프레임 상태를 꺼내 쓰는 최적화에서는 같은 프레임 안에서 그 필드를 읽는 다른 경로를 함께 확인한다.
* `src/syntax.rs`에는 캐시가 없어 호출마다 트리시터 파서와 설정을 새로 만든다. 리사이즈 시 전 이력 × 줄 단위로 재생성된다.
* `session-store.json` 라우트 저장소(`src/backend.rs`)에 만료·개수 제한이 없어 스레드가 영구 누적되고, 저장할 때마다 전체를 다시 읽고 쓴다.
* 상태 컬렉션 대부분은 상한이 있다(서브에이전트 로그 400, 컴포저 undo 100, 턴 경계 clear 등).

## 스트리밍 완료 표시

* 완료 알림을 미룬 뒤에는 뒤따라온 알림도 원래의 순서·스트리밍 보호를 거쳐 재생해야 한다. 보류 배열을 단순히 `dispatch_notification`으로 풀면 중간의 새 delta 뒤 완료가 다시 전량 출력한다. 전환용 저장도 수신 시점이 아니라 화면으로 넘기는 완료 처리 뒤에 해야 마지막 답변이 빠지지 않는다.
* 긴 응답에서 전량 출력 기한만 없애면 짧은 줄이 많은 응답의 애니메이션이 지나치게 오래 남는다. 따라잡기는 프레임별 글자·줄 예산을 함께 두고 숨긴 링크 주소와 유니코드 결합 글자를 보존한다. 이 대기 중에는 백엔드 정체 감지가 별도 완료 알림을 만들지 않게 한다.
* 따라잡기 예산은 고정 글자 수만으로 제한하지 않고 실제 경과 시간에도 비례시킨다. 처리 틱은 터미널이 보여 주는 한 프레임과 같지 않으므로, 여러 틱의 출력이 화면에서 합쳐지는 경우도 고려해야 한다. 완료된 전사에는 부분 응답 수신 간격이 없을 수 있다. 원문 재생은 출력 알고리즘 검증이며 실제 네트워크·화면 정체의 재현으로 설명하지 않는다.

## 세션당 상주 비용

DevezCode 안에서 dvz 세션을 여러 개 열면 세션마다 백엔드 CLI와 MCP 서버 전체가 따로 뜬다. 세션 1개당 약 1.4GB(claude 약 320MB, chrome-devtools-mcp 체인 약 280MB, postgres-mcp 2종 약 380MB, KnowledgeMcp 2개 약 96MB, 나머지 브리지·conhost)가 상주하며, 세션 3개 기준 트리 합계 6.5GB가 관측됐다. MCP 서버를 띄우는 주체는 백엔드 CLI이고 dvz는 설정만 전달한다.

## 정리 방법

* 구버전: `current-executable.txt`가 가리키는 버전만 남기고 `versions` 하위 폴더 삭제.
* 빌드 산출물: 저장소의 `target`은 계속 자란다. 2026-09-13 이 PC에서 96GB였다. 배포본과 무관하므로 디스크가 모자라면 `cargo clean` 또는 오래된 프로필 폴더 삭제로 회수한다.
* 임시 잔여물: `%TEMP%`의 `devez*` 항목 중 진행 중인 테스트 분(최근 수정분)을 제외하고 삭제.
* 고아 프로세스: 부모가 죽은 `postgres-mcp`·`bun`·`conhost`를 PID로 종료. 이후 생성분은 작업 개체가 막지만, 도입 전에 남은 것은 수동 정리가 필요하다.

## 백엔드 무응답과 브리지 재기동

* 세 제공자의 요청·응답(`ClaudeClient::request`, `AppServerClient::request`, `OpenCodeClient::request`)에는 10분 상한 `REQUEST_TIMEOUT`이 있다. 초과하면 대기 항목을 지우고 오류를 낸다. 상한을 늘리거나 줄일 때 사용자 문구는 상수에서 계산하므로 따로 고치지 않는다.
* 상한이 정상 대기를 끊지 않는 근거: Claude `session/prompt`·`session/steer`는 브리지가 턴 번호만 즉시 돌려주고, 사용량 한도 대기는 요청이 아니라 `claude/usageLimit/waiting` 알림으로 오간다. Codex `turn/start`도 턴이 끝나기 전에 응답한다. OpenCode의 프롬프트는 `request()`가 아니라 detached 경로를 쓴다. 멈춘 턴은 `src/state.rs`의 정체 프로브가 따로 끝낸다.
* Codex 권한 프로필 재시도(`request_with_permissions`)는 `permission_configuration_rejected`가 참인 오류에서만 다음 프로필로 넘어간다. 상한 초과 오류는 이 조건에 걸리지 않아 곧바로 반환되므로 상한이 프로필 수만큼 누적되지 않는다.
* Claude 브리지가 끊기면 `outbound`만 비고 프로세스 자리는 남는다. `ensure_started`는 남은 자리를 `ClaudeProcess::discard`로 거두고 새로 띄운다. `discard`는 읽기 작업이 매달린 요청을 깨우고 종료를 알릴 틈을 1초 준 뒤에 거둔다. 곧바로 abort하면 그 정리가 사라져 요청이 상한까지 매달린다.
* 다시 뜬 브리지에는 세션 목록이 비어 있어 이어 말하기가 `Claude 세션을 찾을 수 없습니다`로 실패한다. `BackendServer::claude_turn`이 그 오류에서만 `session/resume`으로 전사에서 되살린 뒤 한 번 다시 보낸다.
* 브리지의 호스트 요청 번호는 프로세스마다 1부터 시작한다. 재기동 후 같은 번호를 쓰면 화면에 남은 옛 질문과 겹쳐 새 질문이 재전송으로 읽히고 버려지므로, id에 실행마다 다른 `HOST_REQUEST_RUN`을 넣는다.
* 브리지가 `claude` CLI를 실행할 때 조회는 60초, 설치·마켓플레이스 변경은 10분 상한을 쓴다. 변경 작업을 조회 상한으로 끊으면 마켓플레이스 폴더가 반쯤 쓰인 채 남는다.
