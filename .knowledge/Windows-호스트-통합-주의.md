## Codex 비동기 질문의 호스트 대기 상태 — 2026-09-10

- 비동기 질문은 제공자 턴이 종료되어도 `AppState.awaiting_input()`이 참이다. `busy=false`만 호스트에 전달하면 DevezCode가 대기 표시를 지우고 완료로 처리한다. `src/devezcode.rs`는 미응답 질문도 호스트의 `running` 상태로 유지한다. 실제 제공자 `busy` 값은 바꾸지 않는다.
- DevezCode의 `MainWindow.xaml.cs`는 UI 큐에서 이벤트를 처리할 때 `ReadRoomActivity`·`ReadRoomWaiting`으로 최신 파일을 다시 읽는다. `idle+waiting`을 보내는 구버전 Vibe도 질문을 유지하며 완료 알림을 보류한다. 질문 해제 후 유휴 상태는 완료 한 번으로 처리한다.
- 수정 전 회귀 검사에서 비동기 질문의 `busy` 파일이 `idle`로 바뀌는 실패를 재현했다. 호스트 검사에서도 역순 이벤트로 `IsBusy`·`IsWaitingChoice`가 모두 거짓이 되는 실패를 재현한 뒤 수정했다.
- 검증: 일반 Rust 검사 1,295개 통과(14개 기본 제외). 추가 수명주기 검사에는 동기·비동기 각각 답변·취소·전송 실패·연결 종료 8개 경로와 중복·100회 대기 틱이 포함된다. 실제 `live_codex_async_question_recovery`도 통과해 Astra 질문 수신·10초 대기·답변 전달·대화 복원을 확인했다.
- `node scripts/test-devezcode-question-state.mjs`는 형제 DevezCode 저장소의 실제 상태 파일 읽기·이벤트 처리·완료 및 대기 알림 판정 코드를 독립 .NET 실행 파일로 검사한다. 재점검 후 구버전 상태 조합·정순·역순·중복·답변·취소·늦은 종료 및 대기 이벤트·복원·압축·짧은 턴·파일 잠금·손상·실제 FileSystemWatcher 원자적 교체 수신까지 15개 시나리오가 통과했다. UI 큐와 타이머는 결정적으로 재생하며 실제 WPF 화면 검사가 아니다. 새 상태 파일은 무작위 시험 방에만 만들고 종료 시 제거한다. 앱 전체를 재시작하거나 상태 감시 서비스의 `Start()`를 호출하지 않는다.
- 재점검에서 UI 처리 전에 끝난 짧은 턴의 완료 기록 누락과, 최신 파일이 잠겼을 때 과거 이벤트를 적용하는 문제를 추가 재현했다. 서비스가 상태 읽기·변경 판정·이벤트 발행을 직렬화하고 같은 상태의 중복 발행을 생략한다. UI는 이미 관측된 턴 시작을 완료 판정에 보존하며, 읽기 실패·손상 시 서비스가 마지막으로 정상 수신한 상태를 사용한다. 빠른 턴은 running이 한 번 관측된 경우를 검사하며 파일 감시가 모든 중간 상태를 놓친 경우까지 보장하지 않는다. Rust 전체 검사도 1,295개 재통과했다.
- 실행 중인 DevezCode 내부 세션이므로 호스트 전체 빌드·재시작·커밋·푸시는 보류했다. 화면 자동화는 native pipe 연결이 `os error 2`로 실패해 실제 앱 화면은 미확인이다. 두 제품 모두 아직 미배포다.
- 이후 사용자의 배포 요청으로 사전 검증을 진행했다. 실행본이 `%LOCALAPPDATA%/DevezCode/DevezCode.exe`임을 확인하고, 설치 경로와 분리한 `%TEMP%/devezcode-question-release-preflight`에 전체 Release 빌드를 수행해 경고·오류 0개로 통과했다. 호스트 15개 시나리오 및 기존 터미널 우클릭 12개 검사도 통과했다. 앱 종료·재시작과 실제 화면 검증은 하지 않았으며, 업데이트 노트 승인 전이라 버전 변경·게시도 하지 않았다.
- 최종적으로 사용자 승인 노트 한 문장만 넣어 Devez Vibe 1.8.23(`6274aad`)과 DevezCode 1.27.2(`bc39aaf`)를 커밋·푸시·배포했다. 공개 패키지·설치 파일·델타 복원 해시와 노트 일치를 검증했다. Vibe는 전역 및 관리 실행 버전도 전환했다. 실행 중인 DevezCode 프로세스는 유지했으며, 호스트 수정은 앱의 정상 업데이트 적용 후 사용된다. 실화면 검증은 미수행이다.

## cmd.exe 검색 명령의 리디렉션 주의

- `cmd.exe`에서는 정규식의 `>`·`&`가 셸 리디렉션·명령 구분으로 해석될 수 있다. 역슬래시는 셸 이스케이프가 아니므로 검색식에 넣지 말고, 셸 메타 문자가 없는 검색어와 `rg -e` 여러 개를 사용한다. 2026-09-09 비교 점검 중 브리지 파일이 비워져 직전 검증 실행 파일의 `include_str!` 원문으로 복구한 사례가 있다.

## ConPTY 입력 변환

자판 대응이 없고 문자 분류상 알파벳도 아니며 전각도 아닌 문자는 ConPTY가 Alt 코드 키 이벤트로 합성할 수 있다. `crossterm`에서는 이 입력이 누름 없이 놓기 이벤트 하나로 도착하므로, 호스트와 `dvz` 사이의 사설 표식 문자는 놓기 이벤트만 와도 문자 입력으로 처리해야 한다.

한글 자모와 완성형 음절은 일반 누름·놓기 흐름으로 들어온다. 사설 표식 예외를 전체 문자 입력에 넓히지 않는다.

외부 터미널(Windows Terminal·conhost)에서는 한글 IME가 조합에 쓴 키의 누름을 가져가고 놓기만 통과시키며, `crossterm`은 놓기 이벤트의 빈 문자를 자판 배열로 되살려 영문 놓기 이벤트로 전달한다. 누름 없는 놓기를 Alt 코드로 보고 누름으로 되돌리면 음절 뒤에 마지막 키의 영문이 덧붙으므로, 외부 터미널에서는 ASCII 문자의 홀로 온 놓기를 되돌리지 않는다. DevezCode 호스트 경로는 텍스트를 직접 보내므로 이 규칙을 적용하지 않는다.

출력 재생 중 한글·이모지·폭 계산이 어긋나는 문제는 `.knowledge/한글-글리프-깨짐-진단.md`를 따른다.

## 호스트 재배선 뒤 상태줄만 빈 채 남는 증상

DevezCode는 재배선·커튼 걷기 뒤 화면을 ConPTY 재방출로 복원하고, 크기가 그대로면 행 수를 1줄 줄였다 되돌리는 킥으로 재방출을 만든다. 이 왕복은 알림 크기가 결과적으로 같아 차분 갱신만 도는데, 화면에서는 행이 빠질 수 있다. 값이 자주 바뀌는 컴포저·스피너는 다음 프레임에 복구되지만 값이 멈춰 있는 상태줄은 사용자가 창 크기나 사이드패널을 건드릴 때까지 빈 채로 남는다.

커서 위치로 외부 화면 쓰기를 감지하는 복구 장치는 이 경로를 잡지 못한다. 킥이 커서를 제자리로 되돌리기 때문이다. 그래서 터미널이 알린 리사이즈는 크기 변화가 없어도 항상 재배치를 무장시킨다. 폴링으로 읽는 크기에는 이 규칙을 넓히지 않는다. 매 틱이 전체 재도색이 된다.

## 배치 파일 안의 PowerShell 본문

- 구분 표식을 찾을 때 명령줄에 적힌 표식이 먼저 잡힐 수 있으므로 첫 위치가 아니라 마지막 위치를 기준으로 본문을 분리한다.
- 파일이 LF로만 저장되면 `cmd`가 `exit /b` 뒤의 PowerShell 본문까지 명령으로 실행할 수 있으므로 혼합 배치 파일은 CRLF로 저장한다.

## 실기기 그래픽 시험 실행 — 2026-09-11

Sixel 모서리 관련 `#[ignore]` 시험(`live_native_terminal_metrics`, `live_native_question_corners`)은 세션 안에서 못 본다. `wt.exe -w new cmd.exe /c <배치>`로 새 창을 띄워 실행한다.

- **표준 출력을 파일로 돌리지 않는다.** `query_graphics`는 `io::stdout().is_terminal()`을 먼저 보므로 `> log.txt`를 붙이면 감지가 통째로 꺼지고 시험이 0.00초 만에 실패한다. 결과는 `DEVEZ_GRAPHICS_TEST_RESULT` 파일로 받는다.
- 창 안의 그림은 화면 캡처(`CopyFromScreen`)로 확인한다.
- 이 PC의 Windows Terminal에서 확인된 값: DA1이 Sixel(4)을 보고하고 셀 크기는 10×20 픽셀이며, 답변 카드의 위·아래 모서리 한 칸이 실제로 Sixel로 그려진다.
- 그려진 모서리의 청록은 글리프 쪽보다 1/255 밝다. `corner()`가 팔레트를 퍼센트로 적는 양자화 때문이며 눈으로 구분되지 않는다. 색이 한 단계 다르다는 이유로 버그로 보지 않는다.
