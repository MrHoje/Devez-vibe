# 도구 호출 실패 진단

세션 로그(`~/.claude/projects/*/*.jsonl`)의 `tool_result` 중 `is_error`가 붙은 항목을 모아 원인을 가른 기록이다. 도구 이름은 앞선 `tool_use` 블록의 `id`로 이어 붙인다.

## 질문 도구 입력이 JSON으로 파싱되지 않는 경우

`AskUserQuestion was called with input that could not be parsed as JSON` 오류가 나면, 그 호출의 입력에는 `__unparsedToolInput` 키 하나만 남는다. 오류 문구가 알리는 원본 크기(예: 3494바이트)보다 실제로 도착한 문자열이 짧아, 입력이 도중에 끊긴 상태다.

- 브리지(`npm/bridge/claude-agent-sdk-bridge.mjs`)에는 도구 입력의 부분 JSON을 이어 붙이는 코드가 없다. 조립과 검증은 SDK 쪽에서 끝나고, 실패하면 `canUseTool`까지 오지 않는다. 따라서 DevezVibe 코드로 가로채 고칠 수 있는 지점이 아니다.
- 관찰된 사례는 모두 한국어 선택지 설명이 길어 입력이 수천 바이트로 커진 호출이었다. 입력 크기를 줄이는 쪽(지침에서 선택지 설명 길이를 제한)이 DevezVibe가 손댈 수 있는 유일한 완화책이다.

## 파일 상태 충돌

- `File has not been read yet`: 해당 세션에 그 경로의 `Read` 기록이 아예 없었다. 경로 대소문자 차이 때문이 아니라 읽지 않고 수정한 경우다.
- `File has been modified since read`: 읽은 뒤 외부에서 파일이 바뀐 경우다. 무엇이 바꿨는지는 로그만으로 가려낼 수 없다.

둘 다 SDK의 사전 검증에서 나며 브리지 경로를 거치지 않는다.

## 작업 트리 검증에 git stash를 쓰지 않는다

변경 전후 테스트를 비교하려고 `git stash`를 쓰면 작업 트리의 사용자 변경까지 함께 치워진다. 그 사이 다른 세션이 같은 파일을 고치면 `git stash pop`이 "local changes would be overwritten"으로 거부되어 복원이 수작업 병합이 된다.

- 기존 실패가 내 변경 탓인지 보려면 stash 대신 `git stash` 없이 `git worktree add`로 HEAD 사본을 만들거나, 실패 테스트 이름으로 원인을 코드에서 직접 확인한다.
- 부득이 stash를 썼다면 되돌리기 전에 `git diff > patch`로 현재 변경을 먼저 백업한다.
