# 응답 미표시 진단

## 먼저 가를 것

"질문 창에 응답이 가렸다"는 보고는 세 경우로 나뉜다. 화면 배치를 고치기 전에 어느 쪽인지 확정한다.

1. 모델이 텍스트를 보내지 않았다.
2. 전달 도중 응답이 빠졌다.
3. 응답은 그려졌지만 배치 때문에 보이지 않는다.

## 확인 순서

1. **Claude 세션 기록:** `~/.claude/projects/<프로젝트>/<세션 id>.jsonl`에서 그 메시지 id의 블록 구성을 본다. 2026-09-23 사례는 `thinking` 다음에 `tool_use:AskUserQuestion`만 있었다. 아래 Opus 5.5 절을 본다.
2. **화면 출력 기록:** `DEVEZ_VIBE_SCREEN_LOG`가 켜져 있으면 터미널로 나간 바이트가 모두 남는다. 파일이 수 GB까지 커지므로 `tail -c`로 뒷부분만 잘라서 찾는다. 문장이 한 번도 없으면 그려지지 않은 것이다.
3. **화면 재구성:** 행·열 이동 좌표의 최댓값으로 화면 크기를 정한다. 질문 창이 열리는 동기화 프레임까지 `pyte`로 재생하면 그 순간의 화면이 나온다. 전사 영역이 맨 아래를 따라가는지, 질문 창이 몇 줄을 차지하는지 여기서 확인한다.

## Opus 5.5 진행 알림 생각 블록(2026-09-23 확정)

- Opus 5는 도구 호출 사이의 설명을 `text` 블록으로 보냈다. Opus 5.5·Fable 5.1은 한두 문장을 넘는 설명을 "진행 알림" `thinking` 블록으로 보내고, 원문은 공개하지 않는다. `thinking.display: "updates"`(베타 `thinking-display-updates-2026-08-18`)일 때만 짧은 요약이 `thinking_delta`로 온다.
- 번들 CLI는 SDK 모드에서도 이 `updates`를 자동으로 요청한다. 실제로 세션 기록의 `thinking` 필드에 설명의 한 줄 요약이 남아 있었다. 출력 토큰은 요약보다 훨씬 많아, 원문이 생각 쪽에서 소모됐다.
- 원문은 순정 Claude Code도 받지 못한다. 초안처럼 그대로 읽혀야 하는 내용은 질문 도구와 같은 응답에 쓰지 말고, 도구 없는 본문이나 도구 입력에 담아야 한다. Claude 주입 지침의 질문 규칙에 이 문장을 넣었다.
- 요약이 화면에 없던 이유는 슈퍼 바이브가 `Thinking…` 블록을 모두 제거하기 때문이다. 브리지는 이 모델들의 비어 있지 않은 `thinking`을 `agentMessage`로 바꿔 보낸다. 실시간 스트림, 부분 이벤트 없는 재생, 기록 복원 모두 같다. 모델 판별은 `PROGRESS_UPDATE_MODEL`이다.
- 세션 기록에서 확인할 때는 `thinking` 필드 길이와 `usage.output_tokens`를 함께 본다. 둘을 비교하면 설명이 생각 쪽으로 들어갔는지 가늠할 수 있다.

## 현재 구현에서 확인된 사실

- 질문·승인 창이 열려 있어도 메인 루프는 `drain_stream_text`로 남은 응답을 계속 드러내고, 휠 스크롤도 막지 않는다. 상태 단위 테스트에서 이 흐름을 재현하려면 `tick`만으로는 안 되고 `drain_stream_text`를 함께 호출해야 한다.
- Claude·Codex의 질문 RPC와 Claude·Codex·OpenCode의 승인 요청 모두 직전 응답이 남는다. `src/question_audit_tests.rs`의 제공자별 테스트가 이를 검사한다.
- Codex 비동기 질문은 질문이 담긴 `agentMessage` 자체만 화면에서 지우고, 앞의 별도 응답은 남긴다. 같은 메시지 안에 설명이 섞여 오는지는 실제 모델로 확인하지 않았다.
- 한국어 대화에서 도구 호출 직전에 오는 한 줄짜리 영어 문장(한글 없음, 160자 이하)은 브리지가 의도적으로 숨긴다.
