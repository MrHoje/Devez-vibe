# Devez Vibe 배포 버전 갱신 절차

버전별 절은 당시 승인·배포·검증 이력이다. 현재 공개 버전과 설치본은 배포 작업에서 별도로 조회하며, 문서의 가장 위 버전을 곧바로 현재 서비스 상태로 간주하지 않는다. 자동 기록 기능의 현재 동작은 [자동 지식 기록과 문서 검색](자동-지식-기록과-검색.md)을 따른다.

## 업데이트 노트 작성과 사용자 검수

- 배포를 요청받으면 변경 사항과 이 문서에 쌓인 배포 대기 항목을 대조해 업데이트 노트 초안을 먼저 작성한다.
- 새 기능, 사용 방식 변경, 사용자에게 영향을 주는 오류 수정만 포함한다. 오탈자, 서식 정리, 내부 정리 등 사소한 변경은 제외한다.
- 항목마다 사용자에게 달라지는 점을 자연스러운 한국어 한 줄로 적는다. 기술 식별자만 원문을 유지하고 내부 구현 설명은 넣지 않는다.
- 초안을 사용자에게 보여주고 검수받는다. **명시적인 노트 승인 전에는 버전 변경과 게시를 진행하지 않는다.** 승인 대기 중에도 필요한 구현과 검증은 마친다.
- 승인받은 문구를 `src/update.rs`의 `RELEASE_NOTES`에 반영한다. 웰컴 화면의 `What's New`는 이 배열의 한국어 업데이트 노트를 표시한다.
- 배포 성공 후 배포 대기 항목을 비우고 승인된 노트를 아래 버전별 이력에 남긴다. 승인 이후 문구가 달라지면 다시 검수받는다.
- DevezCode와 함께 배포할 때는 해당 저장소의 실제 배포 문서를 확인한다. 과거 PC의 절대 경로를 가정하지 않으며 이 프로젝트의 게시 방식은 아래 npm 절차를 따른다.

## 웰컴 UI 버전의 출처

- 웰컴 UI의 `vX.Y.Z` 표기는 `src/update.rs`의 `CURRENT_VERSION`을 사용한다.
- `CURRENT_VERSION`은 `Cargo.toml`의 `package.version`에서 컴파일 시점에 읽는다.
- 따라서 웰컴 UI 버전을 바꾸려면 `Cargo.toml`의 `version`을 변경하고 Release 빌드를 새로 해야 한다. 렌더러의 문구를 직접 수정하지 않는다.

## npm 배포 전 체크리스트

### 저장소에 남길 파일

- 소스·의존성 선언·잠금 파일·지식 문서·재현 검사는 추적한다. `target`, 배포용 임시 빌드, 설치된 `node_modules`, Python 캐시, `.hoje` 개인 세션 상태는 생성물이므로 추적하지 않는다.
- `artifacts`는 기본 제외한다. 호환성 검사 입력인 `codex-compatibility/schema.ts`·`baseline-version.txt`와 `knowledge-search-evaluation`의 명시된 검사기·보고서·비교 결과만 `.gitignore` 예외로 보존한다. 파일 이름만 보고 모든 산출물을 삭제하지 않는다.
- `compatibility-report.md`·`schema-current.ts`는 호환성 검사기가 다시 생성하는 로컬 결과다. 기준 스키마와 구분한다. `.opencode/tools`의 프로젝트 도구는 소스이며 설치 의존성과 함께 제거하지 않는다.
- Git 추적 해제는 과거 커밋의 객체나 원격 파일을 즉시 지우지 않는다. 저장소 이력 재작성은 일반 청소에 포함하지 않는다.

### 배포 순서

1. `git status`·현재 브랜치·upstream을 확인한 뒤 원격을 가져온다. 선형 갱신이 가능하면 `git pull --ff-only`를 사용하고, 로컬 변경이나 분기가 있으면 내용을 보존하며 통합한다. 다른 브랜치에 원격 `main`을 무조건 병합하지 않는다. 원격이나 게시본보다 오래된 코드로 배포하면 최근 변경이 빠질 수 있다.
2. `npm view devez-vibe version`으로 이미 게시된 최신 버전을 확인하고 그보다 높은 새 버전을 정한다.
3. `Cargo.toml`과 `npm/package.json`의 `version`을 같은 새 버전으로 맞추고 `Cargo.lock`·`npm/package-lock.json`의 해당 패키지 버전도 확인한다.
4. `src/update.rs`의 `RELEASE_NOTES`를 사용자가 승인한 업데이트 노트로 갱신한다.
5. `RELEASE_NOTES`의 모든 항목은 자연스러운 한국어로 작성하고, 제품명·명령어·경로 등 기술 식별자만 원문을 유지한다.
6. Release 빌드 후 npm 패키지에 포함할 실행 파일을 교체한다.

```powershell
cargo build --release
Copy-Item target\release\dvz.exe npm\bin\dvz.exe -Force
Set-Location npm
npm pack --dry-run
npm publish --access public
```

7. 공개 버전·패키지 구성·실행 파일 해시와 다음 실행 버전까지 확인한다. 다운로드·전환 실패를 성공으로 기록하지 않는다.

```powershell
npm view devez-vibe version
dvz update
dvz version
```

## 배포 요청 시 범위

- 사용자가 배포를 요청하면 그때까지의 모든 코드 변경 사항을 한 번에 묶어 하나의 새 버전으로 배포한다. 일부만 골라 내보내거나 나중으로 미루지 않는다.
- 배포한 내용은 커밋하고 원격에 푸시하는 데까지 진행한다. 커밋만 남기고 푸시를 미루지 않는다.
- 커밋 메시지는 `release X.Y.Z`로 시작하고, 이번 배포에 담긴 변경을 한국어로 적는다.

## 배포 요청 시 인증 방식

- 사용자가 배포를 요청하면 npm 토큰으로 인증해 배포한다. OTP 입력을 다시 묻지 않는다.
- 토큰은 이미 npm 로그인 상태로 준비되어 있다고 보고, `npm whoami`로 로그인 계정만 확인한 뒤 배포를 진행한다.
- 토큰 인증이 유효하지 않을 때만 사용자에게 알리고, 임의로 다른 인증 수단을 시도하지 않는다.

## 주의

- npm은 이미 게시된 버전을 다시 게시할 수 없다. `npm publish` 전에 `npm/package.json`의 버전이 새 값인지 확인한다.
- 전역 npm 패키지와 관리 실행 버전은 다를 수 있다. `npm install -g`만으로 활성 실행 파일이 바뀌었다고 판단하지 않고 `dvz update` 결과와 새 실행의 버전을 확인한다. 실행 중인 세션이 자동으로 새 바이너리로 교체되는 것은 아니다.
- 소스 빌드는 `target/release/dvz.exe version`처럼 실제 파일 경로로 확인한다. 개인 환경의 `dvz-debug` 별칭 존재를 가정하지 않는다.
